# scripts/

Thin workspace member carrying `install-zed`, the end-to-end SSH deploy of the ZED-box appliance stack. Entry point: `scripts.install_zed.orchestrator:app`, invoked as `uv run install-zed` from the repo root.

## Image acquisition

Three first-party images (`zed-capture`, `aoa-bridge`, `aoa-gateway`) are cross-built arm64 from `compose.bake.yml` — pushed to ghcr by CI, or baked into a transient host-local registry (`--build`; layer-aware pulls across the cable, the iteration path for box logic). The two observability images are **stock** mirror refs (`ZED_STOCK_IMAGES`) pinned by **per-arch arm64 manifest digests** from `.env.lock` — never built locally. The box never pulls from a registry: it is offline, so default mode pulls all five images on the host and ships one gzipped tarball across the cable (`docker save | gzip | ssh … 'gunzip | sudo docker load'`); `--build` keeps registry pulls for the first-party three and ships the stock two by tarball. Digest-pulled images get a transport tag (`STOCK_IMAGE_SHIP_TAG`) before saving — a tagless tarball loses `RepoDigests`, which compose's digest refs need on the box — and a post-load `docker image inspect` proves every reference resolves on the box before compose runs. First-party tree-SHA tags are single-platform arm64: host pulls need `--platform linux/arm64` (plain tag pulls error on amd64 hosts). `compute_service_shas` (docker-devkit) keys the tree-SHA tags.

**Lock updates**: take the `linux/arm64` manifest digest (`docker buildx imagetools inspect <mirror-ref>` — not the index digest, not the attestation entry) into `.env.lock`; CI's `mirror-images` step carries the tag into the org mirror before builds.

## Constraints

- **Micro-B gadget transport, stock config.** The install/deploy/debug channel is the box's micro-USB OTG port: L4T's `nv-l4t-usb-device-mode.service` brings it up as a CDC-ethernet gadget at the stock `192.168.55.1`, serving DHCP to the host — the box configures the host, so no host-side networking state (NM profiles, APIPA fallback, VPN quirks) can block an install. The address is deterministic: no discovery, ever. `install-zed`'s only gadget action is `systemctl enable --now` (idempotent, never bounces a live link); stock config is kept verbatim — rekeying the subnet buys nothing while sandbox filters reject `100.64.0.0/10` like RFC1918. The box's RJ-45 ethernet keeps factory state. USB2 speeds: minutes for the one-time full install, seconds-to-a-minute for layer updates; `--build` iteration rides the same link (the registry reference keys off `$SSH_CLIENT`'s gadget-side host address, which churns across plugs — the insecure-registries presence check re-runs every install).
- **First contact = probe + askpass bootstrap.** `install-zed` polls `192.168.55.1:22` (seconds-scale window — gadget link bring-up is driver bind + NM + box-served DHCP), then bootstraps at that address if the box is virgin. A box that ran a pre-pivot install has the gadget service disabled and needs a one-time enable over ethernet (plan §7). Nothing in the installer ever adds a default route, and the install's closing camera-open assertion trips loudly if one exists.
- **Calibration seeding + offline open.** SDK 5.2 GMSL `open()` fails offline without a local calibration (the EEPROM fallback is 5.3-only), so `install-zed` prompts once for the camera serial (physical label — every on-box read path goes through `open()`, the call that fails), fetches the factory conf from calib.stereolabs.com on the host, and seeds it into the compose bind-mount source `/usr/local/zed/settings`. Unknown serials get HTTP 200 + an all-zero placeholder from the calib service — the installer validates a non-zero `fx` before seeding. The ZEDX `.isp` sensor profiles ride inside the image via the devel build stage (`ZED_DEVEL_DIGEST`); Stereolabs bits never ship standalone. The install ends with the offline camera-open assertion in both modes: success, or the propagated SDK error as the diagnostic.
- **First-contact bootstrap + `SUDOERS_RULE` dormancy coupling.** A virgin Stereolabs box has neither the deploy key nor passwordless sudo, and sudo over ssh has no TTY to prompt on. `_ensure_key_access` in `install_zed/box_install.py` is the bootstrap; its dormancy guard probes `sudo -n systemctl --version` **because that command is in `SUDOERS_RULE`'s list** — `sudo -n true` would be denied even on a bootstrapped box, making the guard never sleep. Corollary: removing a command from `SUDOERS_RULE` (`install_zed/constants.py`) silently breaks the guard's dormancy — keep the guard's probe inside the rule's list. The askpass mechanics and the stdin-tmpfile sudoers dance are documented on `_bootstrap_box_access` — that block comment is the source of truth.
- **USB device-mode is the transport.** `install-zed` *enables* L4T's `nv-l4t-usb-device-mode.service` — it brings up the micro-B CDC gadget the install rides. The phone AOA link runs on the separate Type-A port (always-host); the two never conflict.
- **SSH control-master multiplexer** throughout (single TCP connection reused; socket torn down in a `finally`).
- The appliance strip (masked units, the AOA dialog-respawn rationale), the first-contact bootstrap, and the systemd/camera-daemon ordering are documented in block comments inside `box_install.py` — those comments are the source of truth; this file does not duplicate them.

## Debugging: zed-box SSH access

`ssh zed-box` from a sandbox slot uses the keypair at `/home/code/.ssh-targets/zed-box/id_ed25519`; if it fails with `Permission denied (publickey)`, the sandbox key was never authorized on the box. Run `uv run sandbox authorize zed-box` from the operator's host (once per box/sandbox pair). `install-zed` only installs the operator's personal key — the two paths are independent. Note that coi restricted mode rejects sandbox→RFC1918 traffic by default (the gadget net `192.168.55.0/24` included): a sandbox also needs the one-time host rule pair (forward-accept + masquerade from the sandbox subnet to `192.168.55.1`), and deploys otherwise run from the host shell.
