# scripts/

Thin workspace member carrying `install-zed`, the end-to-end SSH deploy of the ZED-box appliance stack. Entry point: `scripts.install_zed.orchestrator:app`, invoked as `uv run install-zed` from the repo root.

## Image acquisition

Three first-party images (`zed-capture`, `aoa-bridge`, `aoa-gateway`) are cross-built arm64 from `workloads/images.yml` — pushed to ghcr by CI, or baked into a transient host-local registry (`--build`; layer-aware pulls across the cable, the iteration path for box logic). The local bake invocation feeds the service SHAs plus the full `workloads/images.lock` into the env — the same set docker-devkit's `build` verb supplies — because the Dockerfiles' base-image ARGs carry no defaults; a missing key is a hard bake error, not a fallback. The two observability images are **stock** mirror refs (`ZED_STOCK_IMAGES`) pinned by **per-arch arm64 manifest digests** from `workloads/images.lock` — never built locally. The box never pulls from a registry: it is offline, so default mode pulls all five images on the host and ships one gzipped tarball across the cable (`docker save | gzip | ssh … 'gunzip | sudo docker load'`); `--build` keeps registry pulls for the first-party three and ships the stock two by tarball. Digest-pulled images get a transport tag (`STOCK_IMAGE_SHIP_TAG`) before saving — `docker load` synthesizes its own `RepoDigest` instead of restoring the registry one, so a digest ref cannot resolve on the box. The digest pin governs the host pull; the ship tag is what the box `.env` carries and the post-load `docker image inspect` asserts (every reference compose will use). First-party tree-SHA tags are single-platform arm64: host pulls need `--platform linux/arm64` (plain tag pulls error on amd64 hosts). `compute_service_shas` (docker-devkit) keys the tree-SHA tags.

**Lock updates**: take the `linux/arm64` manifest digest (`docker buildx imagetools inspect <mirror-ref>` — not the index digest, not the attestation entry) into `workloads/images.lock`; CI's `mirror-images` step carries the tag into the org mirror before builds.

## Constraints

- **Micro-B gadget transport, stock config.** The install/deploy/debug channel is the box's micro-USB OTG port: L4T's `nv-l4t-usb-device-mode.service` brings it up as a CDC-ethernet gadget at the stock `192.168.55.1`, serving DHCP to the host — the box configures the host, so no host-side networking state (NM profiles, APIPA fallback, VPN quirks) can block an install. The address is deterministic: no discovery, ever. `install-zed`'s only gadget actions are `systemctl enable --now` (idempotent, never bounces a live link) and blanking `net_ipv4_defroute_router` — the config's own documented "leave blank to prevent creating a default route" knob — because the stock scripts otherwise install a default route toward the host on every gadget link-up (L4T's share-the-host's-internet affordance) and the box is offline by design. The stock subnet and composite stay verbatim — rekeying buys nothing while sandbox filters reject `100.64.0.0/10` like RFC1918. The box's RJ-45 ethernet keeps factory state. USB2 speeds: minutes for the one-time full install, seconds-to-a-minute for layer updates; `--build` iteration rides the same link (the registry reference keys off `$SSH_CLIENT`'s gadget-side host address, which churns across plugs — the insecure-registries presence check re-runs every install).
- **First contact = probe + askpass bootstrap.** `install-zed` polls `192.168.55.1:22` (seconds-scale window — gadget link bring-up is driver bind + NM + box-served DHCP), then bootstraps at that address if the box is virgin. A box that ran a pre-pivot install has the gadget service disabled and needs a one-time enable over ethernet (plan §7). Nothing in the installer ever adds a default route, and the install's closing camera-open assertion trips loudly if one exists.
- **Repo-scoped ssh state.** The installer's deploy key and known_hosts live in the gitignored `.placeframe/ssh/`, and every ssh/scp runs `-F /dev/null` with identity and trust files pinned — nothing in the operator's `~/.ssh` is read or written, so a fresh clone bootstraps itself and no other Jetson's known_hosts entry (every L4T gadget answers at `192.168.55.1`) can ever block an install. A changed host key against the installer-owned file means a different or reflashed box — expected churn: `_ensure_box_host_key` resets the file and retries once (TOFU-with-reset; MITM cannot exist on the point-to-point cable). Host-side footprint ends at the repo working tree plus the docker daemon the build/pull modes already use — `rm -rf .placeframe/` undoes the installer's whole host side.
- **Calibration seeding + offline open — headless, camera required.** SDK 5.2 GMSL `open()` fails offline without a local calibration (the EEPROM fallback is 5.3-only), so `install-zed` reads the camera's own serial from the GMSL init banner (printed even while `open()` fails on the missing calibration), fetches that serial's factory conf from calib.stereolabs.com on the host, and seeds it into the compose bind-mount source `/usr/local/zed/settings`. Seeding runs **after** the compose redeploy — the serial probe execs into the running container, and the settings directory bind makes a conf seeded post-`up` visible without a recreate. The install takes no input on this path: an unreadable serial aborts with the probe output (the camera is a prerequisite of the ungated closing assertion anyway), and "already seeded" means the conf for the **probed** serial exists — the settings dir accumulates confs from every camera ever attached, so any-`SN*.conf` is not a signal. Unknown serials get HTTP 200 + an all-zero placeholder from the calib service — the installer validates a non-zero `fx` before seeding. The ZEDX `.isp` sensor profiles ride inside the image via the devel build stage (`ZED_DEVEL_IMAGE`); Stereolabs bits never ship standalone. The install ends with the offline camera-open assertion in both modes: success, or the propagated SDK error as the diagnostic.
- **First-contact bootstrap + `SUDOERS_RULE` dormancy coupling.** A virgin Stereolabs box has neither the deploy key nor passwordless sudo, and sudo over ssh has no TTY to prompt on. `_ensure_key_access` in `install_zed/box_install.py` is the bootstrap; its dormancy guard probes `sudo -n systemctl --version` **because that command is in `SUDOERS_RULE`'s list** — `sudo -n true` would be denied even on a bootstrapped box, making the guard never sleep. Corollary: removing a command from `SUDOERS_RULE` (`install_zed/constants.py`) silently breaks the guard's dormancy — keep the guard's probe inside the rule's list. The askpass mechanics and the stdin-tmpfile sudoers dance are documented on `_bootstrap_box_access` — that block comment is the source of truth.
- **USB device-mode is the transport.** `install-zed` *enables* L4T's `nv-l4t-usb-device-mode.service` — it brings up the micro-B CDC gadget the install rides. The phone AOA link runs on the separate Type-A port (always-host); the two never conflict.
- **SSH control-master multiplexer** throughout (single TCP connection reused; socket keyed per checkout so two clones never ride one master; torn down in a `finally`).
- The appliance strip (masked units, the AOA dialog-respawn rationale), the first-contact bootstrap, and the systemd/camera-daemon ordering are documented in block comments inside `box_install.py` — those comments are the source of truth; this file does not duplicate them.

## Debugging: zed-box SSH access

`ssh zed-box` from a sandbox slot uses the keypair at `/home/code/.ssh-targets/zed-box/id_ed25519`; if it fails with `Permission denied (publickey)`, the sandbox key was never authorized on the box. Run `uv run sandbox authorize zed-box` from the operator's host (once per box/sandbox pair). `install-zed` installs the checkout's own key (`.placeframe/ssh/id_ed25519`) — the two paths are independent. Note that coi restricted mode rejects sandbox→RFC1918 traffic by default (the gadget net `192.168.55.0/24` included): a sandbox also needs the one-time host rule pair (forward-accept + masquerade from the sandbox subnet to `192.168.55.1`), and deploys otherwise run from the host shell.
